# Gonitor 开发升级计划

> 基于当前仓库实现对产品、界面、接口、调度链路、运维能力和研发流程的完整审查与升级规划。  
> 审查依据主要来自：`README.md`、`docs/DEPLOYMENT.md`、`web/client/src/App.js`、`web/client/src/screen/**`、`web/routes/routes.go`、`web/controller/**`、`task/**`、`model/**`、`web/middleware/middleware.go`。

---

## 1. 项目现状总览

Gonitor 当前已经具备一套可用的分布式任务调度与系统监控基础能力，核心链路是完整的：

- 前端提供登录、控制台、任务列表、任务详情、节点管理、用户管理、操作日志页面（`web/client/src/App.js`）
- 后端提供系统信息、任务、节点、Agent、用户、操作日志、推送、版本等接口（`web/routes/routes.go`）
- 调度引擎基于 `robfig/cron`，支持 `cmd` / `http` / `file` 三类任务，以及并行 / 跳过 / 延迟三种并发策略（`task/task.go`、`model/task.go`）
- 支持主节点 + 边缘节点模式，边缘节点通过心跳、拉取任务、上报结果完成协同（`web/controller/agent.go`）
- 支持 WebSocket 实时推送监控指标与任务状态（`web/ws/**`）
- 支持 SSH 一键部署边缘节点（`web/controller/deploy.go`）

**结论：**

当前项目已经具备“能用”的产品雏形，但还没有进入“可规模化交付、可持续运营、可团队协作”的成熟阶段。最大的短板不在单个功能点，而在以下几个层面：

1. **产品能力不够完整**：更偏单任务调度，缺少工作流、告警中心、任务模板、批量操作等中台能力。
2. **用户体验不够稳定**：页面结构清晰，但缺少引导、批量操作、状态闭环、失败诊断链路。
3. **运维治理能力不足**：缺少健康检查、结构化日志、监控指标、备份与恢复、升级迁移能力。
4. **安全与权限薄弱**：权限模型、令牌生命周期、跨域策略、部署安全还有明显提升空间。
5. **测试与发布体系偏弱**：当前更像开发者自测项目，而不是成熟交付型产品。

## 2. 当前页面与功能梳理

## 2.1 前端页面清单

根据 `web/client/src/App.js` 与 `web/client/src/screen/**`，当前主要页面如下：

| 页面 | 路由 | 当前能力 | 现状评价 |
|---|---|---|---|
| 登录 | `/` | 用户登录 | 功能简单直接，但缺少首次登录引导、验证码、密码策略提示 |
| 控制台 | `/admin` | 系统概览、CPU/内存/磁盘/网络监控 | 适合基础看板，但缺少异常摘要、告警入口、趋势对比 |
| 任务列表 | `/admin/taskList` | 任务增删改查、启停、立即执行、筛选 | 是核心页面，但任务管理仍偏“单条编辑”，缺少批量与流程能力 |
| 任务详情 | `/admin/taskInfo/:taskId` | 执行日志、运行状态、输出查看 | 有基础诊断能力，但缺少失败原因聚合、上下文与历史对比 |
| 节点管理 | `/admin/nodeList` | 节点列表、密钥、节点部署、系统信息 | 功能亮点明显，但缺少拓扑、在线质量、升级管理 |
| 用户管理 | `/admin/userList` | 用户增删改查 | 只有“用户”概念，没有角色、权限、审计范围 |
| 操作日志 | `/admin/operationList` | 操作记录分页查看 | 满足基础审计，但检索、过滤、归因、导出能力不足 |

## 2.2 页面层面不合理之处

### 1）信息架构偏“管理后台”，缺少“运维工作台”

- 侧边菜单当前只有控制台、任务、节点、用户、日志五个入口（`web/client/src/screen/layout/ListItems.js`）
- 对于调度系统来说，缺少：
  - 告警中心
  - 调度大盘
  - 任务失败分析
  - 通知配置中心
  - 系统设置 / 权限中心
  - 帮助 / 文档 / 引导入口

**问题本质：** 用户能“管理数据”，但不能高效“处理问题”。

### 2）任务表单能力虽多，但认知负担偏高

任务表单已包含执行方式、优先级、节点、Cron、重试、标签、断言、结果处理器等字段（`web/client/src/screen/taskList/TaskInfoEditForm.js`），但仍有问题：

- 缺少分组展示与新手引导
- 缺少字段级说明与最佳实践模板
- 缺少任务预检查（Cron 解释、命令试跑、节点可达性、HTTP 测试）
- 缺少“高级选项折叠”，导致普通用户第一次接触成本较高

### 3）任务执行结果展示不够“面向排障”

- 任务详情以日志和输出为主，但缺少：
  - 失败原因摘要
  - 断言失败定位
  - 最近 N 次执行结果对比
  - 平均耗时 / 成功率 / 连续失败次数
  - 从任务跳转到通知记录、节点状态、系统事件的联动入口

### 4）节点管理偏“静态资源页”，缺少“运行态治理”

节点页面已经支持密钥、系统信息和 SSH 部署（`web/client/src/screen/nodeList/NodeList.js`），但仍缺：

- 节点在线率、最近心跳延迟、最近异常事件
- 节点版本一致性检查
- 节点任务负载情况
- 节点批量维护（停用、迁移、升级）
- 节点网络联通测试与诊断报告

### 5）国际化与文案一致性不足

前端中中英文混用明显，例如任务表单标题和字段存在英文 UI（`Task Info`、`Execute Type`、`Retry Times`），而其他页面是中文（`web/client/src/screen/taskList/TaskInfoEditForm.js`）。

**影响：** 产品对外展示不够统一，也不利于后续支持多语言。

## 3. 当前接口与调度链路分析

## 3.1 后端接口分层

根据 `web/routes/routes.go`，后端大致分为：

- `system/*`：系统概览与监控数据
- `task/*`：任务 CRUD、启停、试跑、日志
- `node/*`：节点 CRUD、部署、测试、密钥再生
- `agent/*`：边缘节点心跳、拉取任务、回传结果、版本检查、事件同步
- `user/*`：登录与用户管理
- `op/*`：操作日志
- `push/*`：推送测试
- `version`：版本信息

这一分层是合理的，但**中间层能力还不够**，主要缺：

- 统一设置中心接口
- 告警 / 通知中心接口
- 权限 / 角色 / 资源授权接口
- 系统健康检查接口
- 统计分析接口
- 导入导出接口

## 3.2 调度链路现状

当前调度主链路如下：

1. 创建任务，写入数据库（`web/controller/task.go`）
2. 调度器加载任务到内存 `TaskList` 并注册到 Cron（`task/task.go`）
3. 到点后创建执行实例 `RunningInstance`（`task/taskRunning.go`）
4. 执行命令并记录日志、输出、断言结果、结果处理器（`task/taskRunning.go`）
5. 通过 WebSocket 推送任务和系统状态（`web/ws/**`）
6. 边缘节点通过 `/agent/tasks` 拉取分配任务，通过 `/agent/report` 回传结果（`web/controller/agent.go`）

## 3.3 调度设计中不合理或不足的地方

### 1）调度模型还停留在“单任务 Cron”，缺少工作流能力

当前 `Task` 模型核心字段是 `schedule / exec_type / command / retry / exec_strategy / node_id`（`model/task.go`），适合基础定时任务，但不适合更复杂的生产场景：

- 缺少任务依赖（前置任务成功后触发）
- 缺少串并行编排
- 缺少条件分支与失败补偿
- 缺少人工审批 / 人工确认节点
- 缺少手动重跑某一步

**结论：** 现有模型足以做“任务调度器”，但还不足以成为“任务编排平台”。

### 2）缺少任务超时与资源保护机制

当前任务执行使用 `exec.Command(...).Start()` + `Wait()`（`task/taskRunning.go`），但没有看到超时控制、context 取消、运行时间上限等机制。

**风险：**

- 死循环或卡死任务无法自动回收
- 节点资源被单任务长期占用
- 无法定义“最长执行时间”
- 失败恢复只能依赖人工停任务

### 3）远程节点结果回传不完整

`AgentReportTaskResult` 已接收 `exec_output`，但当前只创建一条基础 `TaskLog` 记录，没有落盘输出、没有统一复用本地执行日志链路（`web/controller/agent.go`）。

**影响：**

- 边缘节点任务的排障体验与本地任务不一致
- 远程执行日志难以统一查看
- 后续做失败分析、结果对比、通知模板会受限

### 4）调度状态过于依赖内存

调度器当前使用内存 `TaskList map[int64]*taskInstance` 管理任务实例（`task/task.go`）。

**短板：**

- 重启后运行态丢失
- 不利于 HA / 多实例部署
- 无法自然支持分布式锁
- 难以构建“调度历史视图”

### 5）接口细节存在一致性问题

`/system/net` 当前映射到 `controller.GetDiskInfo`（`web/routes/routes.go`），这说明系统监控接口仍有细节质量问题，需要纳入专项梳理。

## 4. 当前欠缺的关键功能

## 4.1 用户与权限

当前系统只有用户，没有真正的角色与权限模型：

- `CheckToken` 仅校验 token 是否存在（`web/middleware/middleware.go`）
- `UserToken` 有 `ExpiredAt` 字段，但生成 token 时未写入有效期，也未在中间件里校验（`model/user_token.go`）

**欠缺功能：**

- 角色（超级管理员、运维、开发、只读审计）
- 资源级授权（按节点、任务组、项目）
- 菜单权限、按钮权限、数据范围权限
- 会话有效期、强制退出、设备管理
- 密码策略、首次登录改密、二次验证

## 4.2 通知与告警中心

当前系统已具备企业微信推送和结果处理器基础，但还不够形成“告警闭环”：

- 缺少统一通知模板
- 缺少告警规则管理
- 缺少告警收敛、升级、静默、恢复通知
- 缺少多渠道（Webhook、邮件、飞书、钉钉、Slack、Teams）
- 缺少“谁收到什么通知”的订阅机制

## 4.3 调度高级能力

当前缺少的高价值能力包括：

- 工作流 / DAG
- 批量启停 / 删除 / 迁移
- 任务模板
- 环境变量与密钥注入
- 任务执行超时
- 失败重试策略增强（指数退避、仅特定错误重试）
- 任务依赖节点资源选择
- 维护窗口 / 静默窗口
- 补数 / 补跑 / 漏跑处理
- 任务版本管理与回滚

## 4.4 运维与可观测性

当前系统缺少成熟生产运维所需要的能力：

- 健康检查接口
- 结构化日志
- 监控指标导出（Prometheus）
- 容量与性能指标
- 数据备份 / 恢复
- 版本升级迁移方案
- 节点批量升级
- 运行诊断包导出

## 4.5 研发质量保障

当前仓库已有部分 Go 测试，但整体覆盖面还有限，前端也缺少页面级测试。

**欠缺功能：**

- 调度引擎集成测试
- Agent 主从协同测试
- 权限与安全测试
- 前端页面交互测试
- API 契约测试
- 发布前 smoke test

## 5. 分模块升级建议

## 5.1 用户体验与界面升级

### 目标

把现有“后台管理页面”升级为“可用于运维协作的工作台”。

### 建议

1. **重构一级导航**
   - 控制台
   - 调度中心
   - 告警中心
   - 节点中心
   - 审计中心
   - 系统设置

2. **任务页拆分为三层**
   - 任务列表
   - 任务详情
   - 运行分析 / 历史统计

3. **任务表单分组**
   - 基础信息
   - 调度配置
   - 执行配置
   - 高级策略
   - 断言与通知

4. **增加体验型能力**
   - 表单草稿
   - 离开未保存提醒
   - 预校验
   - 批量操作
   - 可复制的失败原因
   - 全局搜索

5. **统一文案与国际化**
   - 统一中文或建立 i18n 方案
   - 保持字段命名一致
   - 为高风险操作增加二次确认与影响说明

## 5.2 调度内核升级

### 目标

从“定时任务执行器”升级为“可编排、可治理、可恢复”的调度平台。

### 建议

1. **补齐任务运行保护**
   - 任务超时
   - 强制终止
   - 最大并发数
   - 节点级并发配额

2. **新增工作流能力**
   - DAG
   - 前置依赖
   - 成功/失败分支
   - 手动审批节点
   - 子任务模板

3. **增强调度治理**
   - 补跑
   - 跳过
   - 重试策略模板
   - 维护窗口
   - 漏跑检测
   - 调度日历视图

4. **统一执行日志模型**
   - 本地 / 远程任务统一日志结构
   - 输出摘要 + 完整日志
   - 失败原因归类
   - 耗时、排队时间、重试次数统一统计

## 5.3 节点与边缘能力升级

### 目标

把节点管理从“可登记、可部署”升级为“可运维、可升级、可诊断”。

### 建议

1. 增加节点心跳质量、延迟、在线率统计
2. 增加节点版本管理与批量升级
3. 增加节点维护状态、摘流、迁移任务
4. 增加节点健康诊断（磁盘、时间同步、网络、Agent 版本）
5. 增加节点分组 / 区域 / 环境标签
6. 增加部署前检查与部署后验收报告

## 5.4 安全与权限升级

### 目标

让系统具备基本的企业级安全基线。

### 建议

1. 建立 RBAC
2. 给 token 加过期时间、刷新机制、吊销机制
3. 优化登录安全
   - 密码策略
   - 登录失败限制
   - 首次登录改密
   - 验证码 / 二次验证（按阶段推进）
4. 收敛跨域策略与敏感接口保护
5. SSH 部署增加主机指纹校验模式
6. 审计日志增加过滤、检索、导出与高危操作标记

## 5.5 运维与观测升级

### 目标

让产品能真正稳定运行在持续交付环境中。

### 建议

1. 增加 `/healthz`、`/readyz`
2. 输出结构化日志
3. 暴露 Prometheus Metrics
4. 增加任务成功率、失败率、平均耗时、节点在线率看板
5. 建立备份恢复与升级迁移文档
6. 增加系统设置页，集中管理日志、数据库、通知、保留周期

## 5.6 测试与交付升级

### 目标

建立可回归、可发布、可追溯的研发流程。

### 建议

1. 后端补充单元测试 + 集成测试
2. 前端补充关键页面交互测试
3. 建立 API 契约回归
4. 增加主从协同的 smoke test
5. 建立发布前检查清单
6. 对高风险模块（调度、权限、部署）单独设质量门禁

## 6. 完整升级路线图

## 6.1 Phase 0：快速修补（1~2 周）

### 目标

先解决影响稳定性、可信度和安全基线的问题。

### 建议交付

- 修复明显接口映射与细节问题，例如 `/system/net` 路由映射核查
- 增加任务超时字段与基础超时控制
- 补齐 token 过期校验
- 收敛默认跨域策略
- 增加健康检查接口
- 统一远程节点任务日志记录
- 优化任务页与节点页的加载 / 错误 / 空状态

### 验收标准

- 任务不会无限运行失控
- 登录态可过期
- 主从任务日志可以统一查看
- 系统具备最基本的运行自检能力

## 6.2 Phase 1：产品基础能力升级（2~4 周）

### 目标

建立“能被团队使用”的基础产品能力。

### 建议交付

- 引入角色与权限
- 任务列表支持批量操作与更多过滤条件
- 节点增加分组、版本、在线质量信息
- 新增通知中心与通知模板
- 操作日志增加搜索 / 筛选 / 导出
- 建立系统设置页面

### 验收标准

- 不同角色能看到不同菜单和操作按钮
- 运维可快速定位失败任务、异常节点和高危操作
- 通知能力从“测试推送”升级为“可配置中心”

## 6.3 Phase 2：调度能力升级（4~8 周）

### 目标

从单任务调度器升级为工作流平台。

### 建议交付

- 任务依赖 / DAG
- 手动审批节点
- 失败补偿与补跑
- 调度日历和运行分析页
- 节点配额与并发控制
- 任务模板与变量体系

### 验收标准

- 可配置多步骤任务流
- 可对失败链路做补偿与重试
- 可从 UI 直接分析任务链路与瓶颈

## 6.4 Phase 3：运维与平台化能力升级（4~6 周）

### 目标

支撑更稳定的线上运行和更低的维护成本。

### 建议交付

- Prometheus / Grafana 接入
- 结构化日志与日志保留策略
- 数据备份与恢复工具
- 节点批量升级
- 灰度发布与版本兼容策略
- 更完善的部署文档与运维手册

### 验收标准

- 能监控系统健康、容量和失败趋势
- 能做版本升级与故障恢复
- 能在多人协作下稳定运营

## 8. 建议的最终产品形态

建议把 Gonitor 逐步建设成一个包含以下能力的统一平台：

1. **调度中心**：Cron + 工作流 + 批量治理
2. **节点中心**：主从节点、边缘部署、升级与诊断
3. **告警中心**：规则、通知、收敛、恢复、订阅
4. **观测中心**：任务、节点、系统、API、日志指标统一分析
5. **权限中心**：用户、角色、资源授权、审计
6. **运维中心**：健康检查、备份恢复、版本升级、配置管理

## 9. 一句话总结

Gonitor 当前的基础方向是对的，亮点也足够明确：**分布式任务调度 + 边缘节点 + 实时监控 + Web 化运维**。  
接下来的升级重点，不应再只是继续堆单点功能，而应该围绕 **“稳定性、可治理性、权限安全、调度编排能力、运维闭环”** 五条主线系统推进。
